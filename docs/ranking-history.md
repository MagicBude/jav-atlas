# 榜单历史与资料补齐

## 榜单变化如何计算

`relay/minnano/rankings.json` 保留当前三榜原始字段；完整三榜另存为 `relay/minnano/ranking-history/YYYY-MM-DD.json`。日期按北京时间计算，同一天手动重复采集会更新当日快照，不增加多份日内历史。

只有每榜250位、人物ID唯一、名次从1到250的完整快照才进入历史。短榜兼容旧采集解析，但不参与名次比较；采集失败也不会建立历史。归档采用临时文件替换，不保证当前榜单和历史多个文件之间的整体事务。

网页构建取当前快照之前日期的最近有效快照，分别比较日、周、月榜。同名人物按 minnano ID 对应；差值为上次名次减本次名次，正数上升、负数下降、零为持平。过去的前250没有该人物时显示“进入前250”，不推断是首次上榜。断更后也只比较最近有效日期，页面明确标出比较时间。

历史来自真实采集。本次从 Git 提交 `731919b55bd72bdd4d7f35cf54eb41de1d309bd6` 恢复2026-10-26快照，并归档现有2026-10-27快照，没有重新访问源站或生成模拟历史。后续每轮采集自动归档；暂未提供历史日期选择器或趋势曲线。

## 人物详情和作品如何继续补齐

人物队列优先选择未成功采集或旧结构记录；成功满30天后每轮最多复查20人，按最旧成功时间优先。字段缺失本身不会触发每日重抓，成功只表示页面解析成功，不表示来源包含全部字段。详情沿用只填空规则，已有非空资料和来源字段不被删除。

`relay/minnano/profile-progress.json` 在实际尝试后记录状态，失败按1、2、4、7天退避，成功清除失败次数。尚未尝试者不计失败；失败刷新不会因为旧资料存在而记成本轮成功。该文件随 Actions 提交，从而跨 runner 生效。

作品沿用已有断点及详情积压优先策略：可执行详情积压达到一轮详情预算时，先暂停列表发现，补完后自动恢复。每日仍最多补50部详情；JavDB 元数据提高为最多30部、90次请求，保持1秒请求间隔及原有限流退避。新作品优先于已匹配资料复查，原评论、原始字段和来源差异继续保留。预算上限不代表每轮一定成功这么多。

运行 `npm run report:works` 可查看人物池、作品列表覆盖、缺详情、未匹配元数据，以及人物详情成功数和当前非空字段数。非空字段统计不等同于源站字段完整率；待重试、未采集、来源未提供不能混为一谈。输出文件使用 `npm run report:works -- --output relay/derived/work-coverage.json`。

Actions 仍使用 Collect atlas data，定时运行自动应用上述规则。手动补齐可选 daily + ranked 并勾选 include_works；不需要运行全站目录采集。实际补齐结果以每轮报告为准。

## 来源值更新与历史

人物成功复查时，profileSource保存最新非空来源值；profileHistory保存变化前后值和采集时间。第一次接入只建立基线，旧名册非空字段继续保留，避免把历史人工修正误认为来源数据。之后当前字段与旧来源基线一致时自动更新；不一致时保留并记录conflicts。空值不删除旧资料，未知字段仍保留。网页个人修改独立存储，不会被来源更新覆盖。人物详情的原始资料中可展开最新来源值和历史。

这项机制替代早期的永远只填空策略；已有记录需下一次成功复查才会建立来源基线。历史随relay提交，后续按真实变化追加，不预填虚构变更。
