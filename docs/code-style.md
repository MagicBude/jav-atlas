# 代码格式与注释约定

文档以项目当前行为为依据：职责、设计原因、数据流、失败边界和已知限制应能直接从代码附近读懂。格式整理保持文件名、执行顺序、请求参数、路径、数据结构及错误处理不变；功能调整使用独立提交。

## 格式

使用 UTF-8、LF、两空格缩进、单引号、无普通语句末尾分号、100 列建议宽度。数组表达式与立即执行函数前必要的防御性分号保留。长字符串、正则及 URL 不为满足行宽强制拆分。

.prettierrc.json 记录统一格式；.prettierignore 排除数据与依赖目录；.editorconfig 提供编辑器设置。采集脚本不依赖格式化工具运行。

格式化工具版本为 Prettier 3.6.2，可从根目录复查：

~~~sh
npx --yes prettier@3.6.2 --check "tools/*.js" ".github/workflows/*.yml" .prettierrc.json
~~~

## 文件与函数说明

文件顶部使用 @file 解释职责、输入输出、环境变量、命令参数、执行顺序与失败边界。路径要区分脚本目录、仓库根和进程工作目录，不能统一简写为 relay/。

函数 JSDoc 先说明算法、设计原因及副作用，再写 @param、@returns、@throws。空串/null 返回、吞掉异常、修改外层状态和直接覆盖文件均须说明。短回调无需逐行机械解释。

注释不代表运行时验证。类型、日期、数值范围与字段完整性没有校验时，不能暗示已通过验证。采集脚本直接执行会联网和写文件，人工复核工具可能覆盖输入，运行说明应交代这些副作用。

## 信息整合

同一代码位置使用一份连贯说明，合并重复句子，不用多套来源标签或修订说明把解释分层堆叠。配置取值依据、故障原因、兼容改版、样本记录与失败行为必须保留在相关位置。

存在错误或过时描述时，将准确规则与设计背景合并表达，不并排保留互相矛盾的断言。例如名册未命中不是性别事实；函数只转换假名时，不能声称会转换汉字读音。

日期、网络表现、数量和性能记录要标为具体样本，说明其作用及适用边界。样本不能变成当前规模或可达性承诺。事实、设计意图与已知缺陷分别写清，但行文应保持一致。

## 流程与失败边界

主流程的阶段注释解释依赖顺序、集合用途、去重和回写条件。数值写明单位，尤其是请求超时、缓存寿命和 worker 间隔。

Promise.all 不会让同步 execSync 并行。单个任务失败、整批失败、停止分页和进程非零退出不是同一件事，需要分别说明。有限影片样本不代表全站目录，单项成功不代表全部产物事务成功。

已知限制在代码附近说明其实际影响和保护意图，不能把意图写成已经可靠实现。例如共享 Map 引用不能当作独立历史快照；直接覆盖目标不具备临时文件替换的失败保护。

## 验证

脚本使用 Node --check 及 Prettier 检查。格式/注释调整通过 Acorn 8.15.0 对照提交前代码解析语法树：忽略注释、位置、字面量原始拼写及无副作用空语句，比较数值、字符串、正则、调用、条件与执行顺序。

工作流使用 YAML 2.8.1 解析后比较配置值，包括 run 字段内完整 shell 文本，确保触发方式、表达式、权限及提交命令不变，再执行 Git 空白检查。

静态检查不能代替源站可达性、数据质量或端到端验收。整理注释时不执行采集，不生成数据。
