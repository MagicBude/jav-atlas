# 网站整体结构优化方案

日期：2026-10-23。状态：调研与待实施方案；本轮不修改现有网页行为。

## 结论

当前网站已经有人物检索、榜单、人物分区、作品详情和本地收藏，但作品被埋在人物详情里；顶部缺少搜索入口，数据说明与核心浏览入口同级，来源技术字段还占据视觉空间。优先改善信息结构和共用规则，再调整色彩与卡片，避免持续追加零散样式。

推荐主导航为“人物 / 作品 / 榜单 / 收藏”，人物仍是默认首页。全局搜索放在导航右侧，数据说明移至页脚并在必要位置保留入口。不单独增加发现页、推荐流、轮播或账号系统。

## 官方参考与证据边界

以下为官方公开页面/说明，查阅于2026-10-23；观察到的事实与针对本项目的建议分别列出。IMDb高级搜索主页面返回403，TMDB前台页面无法读取，因此不声称完成了这两个站点当前界面的逐屏或登录态验收；相关组织方式以官方帮助/开发文档为依据。Letterboxd官方films页面可读取；浏览器可视化访问超时，本轮不以未看到的配色/动效作为结论。

### IMDb：按内容对象组织检索

官方高级搜索说明提供作品、人物、合作关系与主题等查找方式。[高级搜索帮助](https://help.imdb.com/article/imdb/discover-watch/using-the-advanced-search-feature/GLUEUYWPQNPTEVPU)

借鉴：人物和作品都应有独立可访问的检索入口。全局搜索按人物/作品分组呈现结果，作品可用番号定位，不强迫先知道演员姓名。不照搬奖项、票房、地区等缺少数据的筛选。

### TMDB：文本搜索、条件发现、外部ID是不同任务

官方文档把search、discover、find分别定义为文本查找、按评分/日期等条件发现、用既有外部ID查找。[Finding Data](https://developer.themoviedb.org/docs/finding-data)

借鉴：搜索框处理姓名/别名/标题/番号；筛选器处理年份/厂商/演员/评分条件；原生来源ID只用于准确定位和来源追溯。不能把接口文档当成已确认的前台布局，也不把外部ID查找扩展成未经校验的跨源合并。

### Letterboxd：浏览条件与个人收藏用途清晰

官方films页面列出年份、评分、热门时间段、类型等浏览入口；官方支持页明确watchlist与可自建多个lists的用途差异。[Films](https://letterboxd.com/films/)、[Lists与Watchlist](https://support.letterboxd.com/hc/en-us/articles/15179261056143-What-s-the-difference-between-my-lists-and-my-watchlist)

借鉴：榜单负责发现，收藏负责回访，普通资料库负责查找，不把三者混成一张巨大页面。我们保留现有人物爱心收藏，不因此新增看过、想看、自建片单、社交或账户系统。

### Apple TV：先找到对象，再进入详情逐层阅读

官方指南说明可按标题、出演者、主创搜索，进入作品页后继续看相关内容和详细资料。[Find things to watch](https://support.apple.com/en-lamr/guide/tvapp/atvbb35c9fc3/web)

借鉴：作品核心信息、出演者关系、扩展资料与来源原文形成层次，常用操作先出现。我们是资料库，不照搬大幅宣传图、自动播放、购买或视频播放入口。

## 四个主入口的职责

人物页负责从姓名、别名、身体资料或标签找到人物。顶部保持页名、搜索和结果；筛选与结果形成主次，列表/卡片/纵向排列共用同一数据和收藏逻辑。来源ID保持低强调，未知字段不堆满卡片。

作品页是本轮建议新增的关键入口。展示本地已经发现的正式作品，不把占位当作品，不按网络实时请求补资料。支持标题/番号搜索、发行年份、厂商、已关联人物、日期/评分排序以及标准/紧凑密度。日期未知和未补评分保留真实语义；评分筛选只有在用户选定时才排除未知，不把未知当0分。评论全文和来源原文不进入列表索引。

榜单页继续保留日/周/月Top250，作用是发现人物。三榜切换、排列和浏览位置保持；排名与姓名/头像位于同一条目，日期说明集中在区块上方。榜单中已有作品的人物可直接进入其作品分区，不添加每条采集状态徽标。

收藏页继续使用localStorage，只展示用户已收藏人物，并支持当前筛选/排列。导出、导入与资料备份放页内次要操作，不能让备份说明占据主要列表。作品收藏不在本次范围。

## 搜索与筛选的统一规则

导航搜索输入姓名/别名/标题/番号，按人物和作品分组显示实际本地结果，Enter进入完整结果；没有数据时明确当前本地范围，不声称源站不存在。搜索不负责发起采集，也不需要服务器。

人物与作品可以使用不同字段，但控件层级一致：主搜索、少量常用筛选、更多条件、已选条件/清除、结果数/排序/密度。人物已有性别/采集状态筛选不恢复。不能因某个参考站有大量筛选就照搬。

结果变化时回第一页；密度或排列变化不回第一页。浏览条件保存在URL，个人敏感筛选继续沿用现有本地/历史状态规则。独立作品页参数与人物内w前缀参数由适配层转换，不复制两份筛选排序算法，旧链接继续可用。

## 详情与返回路径

人物保持摘要和互斥分区。作品列表在人物内和独立作品库使用同一列表组件；前者限制当前人物，后者限制本地全库。两者打开同一WorkDetail，不复制评分、出演者、来源差异和评论逻辑。

从人物或作品库进入作品后，关闭应回到原结果、筛选、页码、密度、滚动锚点与焦点；原生后退保持原语义。桌面允许详情层，独立/刷新链接显示完整页。尽量只保留一层可操作详情，避免人物→作品→出演者不断叠窗；跳转其他人物时替换当前详情上下文或进入完整页，并保留明确返回入口。

跨源出演者只有已校验对应关系才关联到本地人物；名字相同不能自动合并。来源差异保持在相关字段附近，完整原文与采集时间放最末或独立分区，常用浏览不展示技术文件路径或采集队列。

## 布局方向

宽屏采用有限内容宽度：人物/作品列表页可有左侧筛选栏与右侧结果，详情页用紧凑身份摘要与内容区。中等宽度把筛选移为顶部折叠区；手机显示搜索、筛选按钮、已选条件与结果，筛选面板应用后再更新，不能横向拖动整页。控件位置和按钮样式统一，触控目标留足高度。

保留浅色资料库风格，以中性色、统一边距和字号层级建立主次。减少大块空白、重复边框和无内容的占位区。人物用已有头像；作品未接入封面前用清晰的文字排版，不放大量假封面框。标准密度完整阅读，紧凑密度快速扫描，完整文本始终可进入详情。

## 代码与数据模块

AppShell只负责导航、全局搜索入口和容器；页面不内嵌采集逻辑。建议增加features/works/WorkBrowser.tsx、WorkFilters.tsx、WorkList.tsx和统一query模块，供人物作品区与独立WorksPage组合。人物PersonCard、头像、收藏、Modal、返回位置与数据读取器继续复用。

构建时新增独立作品轻量索引：来源/原生ID、标题、番号、日期、厂商、关联人物ID、已有评分摘要和详情资源引用。按作品原生ID去重，多出演人物不重复计作品。只有列表关系但详情待补的作品仍可浏览列表并访问来源；评论、原始字段与图片不打包进索引。详细来源记录独立按需加载，沿用内容hash版本。

当前资料保留原生ID和来源目录，不引入新的自建业务ID、后端数据库、账号系统或新的状态管理框架。先通过模块组合整理现有React代码，数据结构只增加必要的派生索引。

## 实施顺序与验收

第一步实现独立作品索引与作品页，并抽出共用WorkBrowser，验证与人物内搜索/排序结果一致、共享作品去重、无详情条目不消失、原始文件不变。

第二步统一AppShell导航和全局搜索，数据说明移到次级入口；验证旧URL、键盘操作、分组搜索与浏览器后退。

第三步统一列表页筛选/结果工具栏和宽窄屏布局，清理散落的覆盖CSS，将页面样式收回各功能模块；不一次改动数据与收藏协议。

第四步精简详情打开/关闭的层级，测试人物列表→人物→作品→返回整条路径和手机布局，最后再决定是否接入封面。

本方案是下一阶段设计，不代表这些新增入口已经实现。每一步分别提交，并区分自动测试、代理浏览器验收与用户接受。
